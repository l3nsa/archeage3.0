### 4.1 Анализ криптографии (`crynetwork.dll`)

**Цель**: верифицировать правильность реализованного XOR/AES и найти все константы, специфичные для версии 3.0.3.0.

#### Что уже известно (из кода)

```csharp
// Деривация XOR-ключа (EncryptionManager.cs:StoreClientKeys)
head = (head ^ 0x15A0248E) * head ^ 0x070F1F23;   // Магические константы 3.0.3.0
XorKey = head * head & 0xFFFFFFFF;

// S→C stream-шифр (StoCEncrypt)
cry = (uint)(length ^ 0x1F2175A0);
cry += 0x2FCBD5;  // инкремент на каждый байт

// CRC8
checksum = checksum * 0x13 + byte;
```

#### Инструкция по исследованию с x64dbg

##### Шаг 1 — Подготовка окружения

```
1. Установить x64dbg (x64dbg.com) — только x32dbg для 32-bit клиента ArcheAge
2. Запустить ArcheAge.exe от имени администратора
3. Открыть x32dbg → File → Attach → выбрать процесс ArcheAge.exe
4. Загрузить символы: Symbols → crynetwork.dll → правый клик → "Load Symbols"
```

##### Шаг 2 — Найти функцию шифрования

```
Метод A — по строке в памяти:
  Search → All Modules → String → искать "encrypt" / "decrypt" / "crynetwork"

Метод B — по импортам:
  Symbols → crynetwork.dll → смотреть экспортируемые функции
  Ключевые: CCrypto::Encrypt, CCrypto::Decrypt, CCrypto::Init

Метод C — по вызовам из send():
  В crynetwork.dll найти функцию, которую вызывают перед send()
  Поставить BP на ws2_32.dll!send
  При остановке — посмотреть call stack выше
```

##### Шаг 3 — Трассировка процесса шифрования

```
1. Поставить breakpoint на вход в функцию шифрования
2. Когда клиент отправляет пакет (например, движение):
   - RAX/ECX = указатель на буфер с данными
   - RDX/EDX = длина буфера
   - RCX/стек = ключ шифрования (он нас интересует!)
3. Шаг за шагом (F7) проследить через:
   - XOR-преобразование: cry += 0x2FCBD5 → проверить константу
   - AES-блок: 16-байтная обработка → записать ключ и IV
   - RSA-использование: обычно только при handshake
```

##### Шаг 4 — Проверить константы для версии 3.0.3.0

```
Проверить в дизассемблере следующие hex-значения:
  0x2FCBD5    — инкремент XOR-потока
  0x1F2175A0  — начальное значение cry для S→C
  0x15A0248E  — первая константа деривации XOR-ключа
  0x070F1F23  — вторая константа деривации XOR-ключа
  0x13        — множитель CRC8

Если константы отличаются от кода — ОБНОВИТЬ EncryptionManager.cs!
```

##### Шаг 5 — Анализ AES-ключа в памяти

```
1. После handshake — поставить BP на AES-decrypt в crynetwork.dll
2. Прочитать аргументы: ключ (16 байт), IV (16 байт)
3. Сравнить с тем что приходит в CSAesXorKeyPacket
4. Проверить режим: CBC vs ECB (искать XOR с предыдущим блоком)
```

#### Контрольные точки верификации

- [ ] Константы XOR совпадают с кодом: `0x2FCBD5`, `0x1F2175A0`
- [ ] Константы деривации ключа совпадают: `0x15A0248E`, `0x070F1F23`
- [ ] AES режим подтверждён как **CBC** (не ECB/GCM)
- [ ] IV — первые 16 байт расшифрованного предыдущего пакета
- [ ] CRC8 множитель = `0x13`
- [ ] Сервер может принимать и расшифровывать movement-пакет без ошибок
- [ ] Сервер может отправить SC-пакет, который клиент принимает без разрыва

#### Частые проблемы и их решение

| Симптом | Вероятная причина | Проверить |
|---------|------------------|-----------|
| Клиент отключается сразу после входа | Неверный XOR-ключ в S→C | `StoCEncrypt`, константа `0x1F2175A0` |
| Пакеты C→S не расшифровываются | Неверная деривация XorKey | Коэффициенты `0x15A0248E`, `0x070F1F23` |
| Расшифровка даёт мусор | Неверный IV для AES | `ConnectionKeychain.IV` обновляется? |
| SCMessageCount overflow | Счётчик выходит за byte | Проверить `IncSCMsgCount()` |
| Разрыв при длинных пакетах | Неверный расчёт длины | `StoCEncrypt` — `length ^ 0x1F2175A0` |

#### Метод A — Статический анализ дизассемблером

##### Поиск switch-case диспетчера пакетов

```
Инструменты: IDA Pro (предпочтительно) или Ghidra (бесплатно)

1. Открыть crynetwork.dll (или ArcheAge.exe)
2. Functions → искать функцию с большим количеством переходов (jumptable)
   Признаки:
   - Функция получает uint16 на входе
   - Содержит JMP [reg*4+offset] — таблица прыжков
   - Сотни case-ветвей

3. В IDA: Graph View → найти узлы с паттерном:
   MOV cx, [esp+...]   ; читаем opcode
   SUB cx, 0           ; нормализация
   CMP cx, 0x2FF       ; граница switch
   JA  default_handler
   JMP [eax*4 + jump_table]

4. В Ghidra: Decompiler → искать функцию с паттерном:
   switch(opcode) { case 0x084: handle_move(); ... }
```

##### Автоматическое извлечение таблицы прыжков (IDA Python)

```python
# IDA Python скрипт для извлечения jump table
import idc, idautils, idaapi

def find_switch_tables():
    results = []
    for func_ea in idautils.Functions():
        func = idaapi.get_func(func_ea)
        if func is None:
            continue
        # Поиск switch info
        si = idaapi.get_switch_info(func_ea)
        if si and si.ncases > 50:  # только большие switch
            results.append({
                'addr': hex(func_ea),
                'cases': si.ncases,
                'jumps': si.jumps
            })
    return results

tables = find_switch_tables()
for t in tables:
    print(f"Switch at {t['addr']}: {t['cases']} cases")
```

##### Извлечение структуры пакета через Ghidra

```python
# Ghidra Script (Java) — поиск функций-обработчиков пакетов
# Запуск: Script Manager → создать новый скрипт → вставить:

from ghidra.program.model.listing import CodeUnit

def find_packet_handlers():
    func_manager = currentProgram.getFunctionManager()
    for func in func_manager.getFunctions(True):
        name = func.getName()
        # Ищем функции вида Handle_XXXX или Process_XXXX
        if name.startswith("Handle") or "Packet" in name:

find_packet_handlers()
```
